What the redraw shows

The value slot is carrying an absence. “the remainder, not in the store” sits where every other row puts a figure, so it parses as a quantity before it parses as a sentence.

Two units, two cards, no relationship. Skills are priced in tokens, servers in bytes. The same reader compares them minutes apart.

The tier that matters has no number. A skill’s name and description are in every engine’s startup list whether or not it ever fires. That is the only cost the user pays unconditionally, and the card states it as a claim rather than a figure.

E

Where it actually goes

Kept as the record of an argument that failed. The pitch was: a total tells you a server is heavy, a ranking tells you which four tools made it heavy. The flaw is in the word “act”. You cannot act on it. You do not choose a tool by the size of its description, you cannot edit a third-party server’s descriptions, and two tools you would never compare on merit are put side by side here purely because one is wordier. The bars measure the one axis nobody uses. What survives from E is the instinct that the per-tool list is worth having — see A + E, where it is kept and the figures are dropped.

What actually changes in the code

MCP: the whole change is deletion. Out of ProbedToolList come the header row, the Schema column, and the per-tool byte figure. Nothing is added — no sort, no totals row, no aside. The list keeps the order the server exposed it in, and a probed tool is { name, description } and nothing else, so what is left on a row is exactly what the tool is.

Every figure moved to the ledger, and only the total survived the move. A per-tool size is accounting sitting in a content list: you do not choose a tool by how wordy it is, and you cannot edit a third-party server’s descriptions, so the number has no decision attached to it. The server-level total does — whether to keep the server. So the ledger holds it and the list holds none.

Two sections, two jobs, no overlap. The ledger answers “what is this costing me” in one place with one figure per tier. The list answers “what does this thing do” and is now readable as prose rather than scanned as a table. Neither restates the other, which is why the header row, the Schema column, the totals row and the per-tool bytes could all go without anything taking their place.

Skill, two edits. Full ink on the Contents row the Context figure came from, muted on the rest; one footnote saying the rest is excluded.

The header row and the Schema column both go. The rows were never a grid — a name and a figure on one line, the description full-width beneath — so “Description” sat above a byte count while the description itself ran underneath it, unheaded. And a column that has always held — is not a column. Both were doing the ledger’s job badly; the ledger now does it. The section aside names the sort, which is what tells you the figure is a description size in the first place.

Tokens lead, bytes support — in the ledger. Tokens are what the reader is spending; bytes are what Hanger measured. So in the ledger the token figure takes the 13px step and full ink, with the byte count beneath it at 11px. The table stays in bytes throughout, totals row included: there the question is which tool is heavier than which, an exact figure serves a ranking better than a divided-by-four one, and one unit per column beats two. The ledger’s second line is what ties the two together — the same 2.8 kB appears in both.

Two honest gaps. A single-file skill has no Contents card, so there is nothing to fold and the ledger stands alone. And a server with more than one launch spec draws one tools block per spec (specGroups), while cost is read from anyVerified — one ledger over several tables. That case needs its own answer before this ships.
